# Актуализированный план MVP Loopkeeper

_Статус: черновик для согласования. Обновлено: 2026-09-22._

## 1. Цель MVP

Создать локально запускаемый backend для ведения настольных ролевых кампаний. Мастер создаёт изолированную кампанию, подключает игроков или наблюдателей, ведёт материалы и заметки, а игроки работают только с данными кампаний, к которым подключены.

Первая игровая система — **Tales from the Loop**. Архитектура должна позволять добавлять системы и шаблоны позже, но MVP не требует реализации второй системы.

## 2. Границы scope

### Входит в MVP

- пользователи: регистрация, вход, профиль, изменение профиля, безопасная смена пароля;
- JWT access token и refresh-сессии с ротацией, выходом и отзывом;
- кампании как tenants: создание, чтение, изменение и удаление владельцем;
- участники с ролями `PLAYER` и `VIEWER`;
- прямое добавление участника и одноразовые invitation links;
- сущности игровой системы и шаблона персонажа;
- один seed-шаблон Tales from the Loop;
- персонажи игроков и NPC;
- заметки с visibility и tenant-фильтрацией;
- раздатки с `fileUrl` и visibility;
- совместный стол расследования: заметки, улики, локации и связи между ними;
- timeline как простой CRUD-модуль;
- Swagger, validation, единая обработка ошибок, unit/e2e-тесты;
- Docker-окружение для локального запуска приложения и PostgreSQL.

### Не входит в MVP

- облачное или production-развёртывание;
- Redis, очереди, WebSocket, уведомления, метрики и централизованный аудит;
- RS256, key rotation, JWT blacklist;
- загрузка файлов в S3/объектное хранилище;
- поиск, теги, Markdown-редактор и история версий;
- production-фронтенд; фронтенд для локальной работы запланирован отдельным следующим шагом после этапа 3.
- AI-функции.

## 3. Модель доступа

### Tenant boundary

`Campaign` — tenant. Любой запрос к кампанийным данным должен в одном из первых шагов:

1. определить текущего пользователя из access token;
2. найти кампанию по ID;
3. проверить, что пользователь — `owner` или имеет `CampaignMember` для этой кампании;
4. применить дополнительную проверку роли/владельца;
5. выполнять Prisma-запрос с `campaignId` в условии.

Нельзя делать запрос «по ID сущности», а затем возвращать/изменять её без проверки принадлежности кампании. Идентификаторы пользователя из body/params не являются основанием для выдачи прав.

### Роли

| Субъект          | Права                                                                                              |
| ---------------- | -------------------------------------------------------------------------------------------------- |
| `Campaign.owner` | Единственный мастер. Полный доступ к данным кампании, её настройкам, участникам, NPC и материалам. |
| `PLAYER`         | Доступ к разрешённым данным кампании, собственному персонажу и совместному столу расследования.    |
| `VIEWER`         | Только чтение общего контента, явно доступного наблюдателям; не участвует в столе расследования.   |

Владелец не дублируется в `CampaignMember`, поэтому `MASTER` не является значением member-role.

### Видимость

Согласованная семантика visibility:

| Visibility    | Кому доступно                               |
| ------------- | ------------------------------------------- |
| `PRIVATE`     | Только автору.                              |
| `MASTER_ONLY` | Владельцу кампании.                         |
| `PLAYERS`     | Владельцу и участникам `PLAYER`.            |
| `PUBLIC`      | Всем участникам кампании, включая `VIEWER`. |

«Public» означает доступ внутри кампании, а не анонимный интернет-доступ.

## 4. Контракты и модель данных

### Пользователи и сессии

`User` хранит email, password hash, имя, avatar URL, timestamps и soft-delete flag. Публичные ответы никогда не содержат `passwordHash`.

Добавить `AuthSession`:

- `id`;
- `userId`;
- `refreshTokenHash`;
- `expiresAt`;
- `revokedAt` nullable;
- `createdAt`, `updatedAt`;
- опционально `userAgent` и IP только для локального диагностического контекста.

Refresh JWT содержит идентификатор сессии (`sid`) и пользователя (`sub`). При обновлении токена текущая сессия отзывается, создаётся новая сессия с новым hash и выдаётся новый refresh cookie. Logout отзывает сессию и очищает cookie. Смена пароля отзывает все пользовательские сессии.

Это даёт практичную локальную безопасность без Redis и blacklist.

### Кампании и участники

- `Campaign`: название, описание, обложка, владелец, игровая система, timestamps.
- `CampaignMember`: campaign ID, user ID, роль `PLAYER`/`VIEWER`, timestamps, уникальность `(campaignId, userId)`.
- `CampaignInvitation`: campaign ID, приглашённая роль, токен в hash-виде, срок действия, время принятия/отзыва, создатель.

Прямое добавление пользователя выполняется по точному email или user ID — выбор контракта нужно зафиксировать. Для API и UX предпочтителен email, с нормализацией и уникальным поиском.

### Игровые системы и персонажи

- `GameSystem`: имя, описание, стабильный slug.
- `CharacterTemplate`: `systemId`, имя, JSONB schema, версия/active flag при необходимости.
- `Character`: `campaignId`, `ownerId` nullable для NPC, `templateId`, имя, JSONB `data`, `isNPC`, description/avatar URL, timestamps. У игрока один активный персонаж в кампании; владелец создаёт неограниченные NPC.

Данные персонажа валидируются относительно schema шаблона на стороне приложения. В MVP достаточно ограниченной декларативной схемы полей: `name`, `type`, `required`, `min`, `max`, `options`; не требуется полноценный JSON Schema engine.

### Стол расследования

Стол расследования — общее рабочее пространство одной кампании для владельца и игроков. Он представляет карту расследования, где участники совместно фиксируют факты и гипотезы в универсальных карточках и связывают их между собой. Карточка может описывать NPC, улику, локацию или любой другой объект, но backend не разделяет их на доменные типы.

Модель MVP:

- один `InvestigationBoard` на кампанию;
- `InvestigationCard`: `campaignId`, заголовок, содержимое, свободные теги, опциональные `color` и `icon`, `createdBy`, timestamps;
- `InvestigationLink`: `campaignId`, пара card ID и необязательная подпись связи, `createdBy`, timestamps;
- `InvestigationBoardNode`: card ID и координаты/размер карточки — данные раскладки для будущего фронтенда.

Теги — произвольные строки. Цвет сохраняется как валидируемое CSS-значение, а иконка — как безопасный ключ из набора, который определит фронтенд; загрузка изображений и произвольных файлов в MVP не поддерживается. Связь ненаправленная: пара карточек нормализуется, чтобы одна и та же связь не создавалась дважды.

Владелец и любой `PLAYER` могут создавать, изменять и удалять любые карточки и связи этого стола. `VIEWER` и внешний пользователь не видят стол. Связи проверяются на принадлежность обеих карточек той же кампании.

В MVP стол не заменяет приватные заметки мастера: `MASTER_ONLY` и `PRIVATE` заметки остаются отдельными сущностями. Карточки не имеют связей с доменными сущностями `Character` или `Handout`; при необходимости участники описывают их обычной карточкой.

## 5. Безопасность для локального MVP

### Требуется

- Argon2 для паролей;
- короткоживущий access token и rotating refresh token, хранимый только hash-значением;
- refresh token в `HttpOnly`, `SameSite=Lax` cookie; `secure: false` только для HTTP localhost, `true` при HTTPS;
- очистка cookie и отзыв сессии при logout;
- in-memory throttling для `login`, `refresh`, `register` и смены пароля;
- `helmet`, явный CORS allow-list для localhost frontend;
- строгий `ValidationPipe`, DTO, whitelist и единый HTTP exception filter;
- отсутствие `passwordHash`, refresh token и внутренних полей в API-ответах;
- хранение secrets в `.env`, без дефолтных production-секретов и небезопасного admin password в seed;
- проверка tenant/role в каждом кампанийном endpoint.

### Отложено осознанно

Redis-based revoke lists, refresh replay detection across a token family, RS256/key rotation, CAPTCHA, централизованные audit logs и metrics. Они оправданы при публичном/многосерверном размещении, которого пока нет.

## 6. Этапы реализации

Каждый этап завершается migration, Swagger-документацией для новых endpoint’ов, unit-тестами сервисов/guards и e2e happy-path + forbidden-path сценариями.

### Этап 0 — стабилизация базы

**Цель:** устранить расхождение существующего кода с будущим контрактом.

- Сохранить локальный Docker Compose, добавить приложение, healthcheck и воспроизводимый запуск миграций.
- Нормализовать routes: `/campaigns`, `/users` и `/auth`.
- Включить глобальный JWT guard с точечным `@Public()`.
- Добавить единый exception filter и корректные HTTP-ошибки (`400`, `401`, `403`, `404`, `409`).
- Безопасно переделать seed: обязательный пароль в окружении или явное разрешение dev seed.
- Настроить тестовую БД/fixtures так, чтобы e2e не зависели от ручного состояния.

**Готово, когда:** проект поднимается локально одной документированной командой; существующие endpoints имеют единый контракт; health и тестовая БД воспроизводимы.

### Этап 1 — пользователи и безопасная аутентификация

**Цель:** пользователь может самостоятельно начать и безопасно завершить сессию.

- `POST /auth/register` с проверкой уникальности email.
- Login, `me`, изменение своего профиля и change password.
- `AuthSession`, hash refresh token, rotation, logout и отзыв сессий при смене пароля.
- In-memory throttling, Helmet, локальный CORS и cookie-конфигурация.
- E2E: register → login → me → refresh → logout; неверные credentials, истёкшие/отозванные refresh tokens, duplicate email.

**Готово, когда:** нет открытого создания/изменения чужого пользователя; refresh token нельзя использовать после logout или ротации.

### Этап 2 — tenant-кампании, membership и invitations

**Цель:** корректная изоляция кампаний и права доступа.

- Владелец кампании создаётся только из JWT пользователя.
- Владелец может менять/удалять только собственную кампанию.
- Список кампаний возвращает только owned/member campaigns.
- CRUD membership с ролями `PLAYER`/`VIEWER`.
- Прямое добавление по email/user ID.
- Создание, принятие и отзыв invitation links.
- Общие `CampaignAccessGuard`/policy helpers для owner/member/role checks.
- E2E: пользователь из другой кампании получает `404`; факт существования tenant-ресурса не раскрывается.

**Готово, когда:** невозможно прочитать или изменить любой кампанийный ресурс без связи с кампанией.

### Этап 3 — игровые системы и персонажи

**Цель:** игроки и мастер ведут листы персонажей внутри tenant.

- Миграции `GameSystem`, `CharacterTemplate`, обновлённого `Character`.
- Seed Tales from the Loop и одного character template.
- Создание и редактирование собственного персонажа игроком.
- Создание и управление NPC владельцем.
- Валидация `data` по schema template.
- Проверки ownership, campaign membership и запрета межtenant-доступа.

**Готово, когда:** персонаж нельзя создать в чужой кампании, привязать к чужому шаблону или изменить неавторизованным пользователем.

### Этап 4 — заметки и visibility

**Цель:** мастер и игроки получают управляемое пространство знаний.

- `Note`, enum visibility, CRUD и scoped list.
- Политика видимости из раздела 3 после согласования.
- Автор может править свои разрешённые заметки; владелец модерирует кампанийный контент.
- E2E-матрица visibility для owner/player/viewer/outside user.

**Готово, когда:** список и получение отдельной заметки применяют одинаковую политику видимости.

### Этап 5 — совместный стол расследования, раздатки и события

**Цель:** дать игрокам и мастеру общее визуализируемое пространство для ведения расследования внутри кампании.

- `Handout` с метаданными, visibility и валидируемым `fileUrl`.
- Один `InvestigationBoard` на кампанию.
- Универсальные карточки без жёстких типов: ими можно описывать заметки, NPC, улики, локации и любые другие факты.
- Свободные теги, настройка цвета и иконки карточки; без загрузки изображений или файлов.
- Ненаправленные связи между карточками с необязательной текстовой подписью (например, «видели рядом», «принадлежит», «ведёт к»).
- Данные раскладки карточек, чтобы будущий UI мог показать их как карту расследования.
- Полностью совместное управление: владелец и любой игрок изменяют и удаляют любые карточки/связи; `VIEWER` не имеет доступа.
- `TimelineEvent` как отдельный tenant-scoped CRUD-модуль.
- Миграции, Swagger и e2e-тесты изоляции кампаний, ролей и ownership.

**Готово, когда:** игроки одной кампании совместно создают карту расследования и связи, не видят данные других кампаний, а `VIEWER` и внешний пользователь получают `404`.

### Этап 5.5 — локальный фронтенд (следующий шаг)

**Цель:** дать MVP рабочий пользовательский интерфейс после стабилизации auth, tenant-модели и контрактов персонажей.

- Начать после этапа 3; после этапа 2 допустимо подготовить только технический каркас и авторизацию.
- Реализовать React-клиент для локальной работы с login, списком кампаний, участниками, персонажами, заметками и раздатками.
- В этапе 5 подключить интерактивную карту стола расследования: карточки, связи и сохранение раскладки.
- Использовать Swagger/OpenAPI как источник API-контракта; не дублировать правила доступа во фронтенде — он лишь отображает решения backend.

Фронтенд не блокирует завершение backend MVP, но является ближайшим планируемым продуктовым шагом после этапа 3.

### Этап 6 — финализация качества и документации

**Цель:** сделать MVP воспроизводимым и проверяемым.

- Проверить все DTO, response DTO и Swagger examples.
- Увеличить unit-тесты сервисов, guards и visibility policies.
- Полный e2e-набор по auth, tenant isolation, roles и основным CRUD.
- Docker Compose для app + PostgreSQL, `.env.example`, инструкции локального старта.
- Финальная security review: секреты, CORS, cookies, rate limits, лишние поля в ответах.

**Готово, когда:** чистая локальная среда поднимает приложение и БД по README, migration/seed выполняются предсказуемо, а тесты покрывают критические пути.

## 7. Порядок начала работ

После согласования открытых вопросов первым изменением должен стать **Этап 0 + Этап 1**. Они устраняют существующие риски (недоступная регистрация, отсутствующий logout, небезопасный refresh flow, открытые пользовательские маршруты) и дают корректную основу для tenant-логики следующего этапа.
